01 — General explanation

The big picture

Two tools you will touch every single day as a developer.

Markdown

A lightweight markup language that formats text with simple symbols like #, *, and -. It powers READMEs, documentation, notes, and chat apps like GitHub, Notion, and Discord.

Visual Studio Code

A free, fast, and extensible code editor by Microsoft for Windows, macOS, and Linux. Extensions turn it into a full workstation for any language, with a built-in terminal and Git.

i
Why together? You write Markdown inside VS Code, preview it live, and push it to GitHub where it renders automatically as your project's front page.
02 — Important points

Key points to remember

Files end with .md

Any README.md in a repo is rendered automatically on GitHub as the project's homepage.

Plain text is future-proof

It opens in any editor and shows clean line-by-line diffs in Git.

Blank lines matter

Separate paragraphs, lists, and headings with an empty line. Missing blank lines are the #1 cause of broken rendering.

One H1 per document

Use # for the title and ## / ### for structure, like chapters in a book.

Open folders, not files

Open the whole project folder in VS Code so search, Git, and the terminal all work on the same scope.

Command Palette is the master key

finds any feature by name. You never need to memorize menus.

02 — Important points

Key points to remember

Always know where you are

Run pwd before any action. Most mistakes happen in the wrong folder.

Tab completes, ↑ recalls

Tab finishes file names for you, and the up arrow brings back previous commands.

Quote names with spaces

Write cd "My Folder", or better, avoid spaces and use my-folder.

There is no Recycle Bin

rm deletes permanently. Read the command twice before pressing Enter.

Ctrl+C stops, not copies

In a terminal it cancels the running command. Copy with Ctrl+Shift+C or right-click.

Flags change behavior

Options like -l or --all modify a command. Run command --help to see them all.

Case matters on Mac/Linux

Readme.md and README.md are different files there. Windows usually ignores case.

Silence means success

Many commands print nothing when they work. Errors are always printed.

04 — Important points

Paths: the map of your computer

A path is the address of a file or folder.

SymbolMeans
/Root, the very top of the drive (C:\ on Windows).
~Your home folder, e.g. /Users/sam.
.The current folder.
..The parent folder, one level up.
-With cd -, the previous folder you were in.

Absolute vs relative

Absolute starts from root and works anywhere. Relative starts from where you are now.

# absolute
cd /Users/sam/projects/module-1
# relative (from projects)
cd module-1
# up one level, then into another
cd ../day-2

10 — Rare but must know

Danger zone

Commands that can destroy work in one keystroke.

rm -rf /Never

Force-deletes everything from the root. It can wipe the whole system.

rm -rf *Danger

Deletes everything in the current folder. Always run pwd first.

curl … | bashDanger

Runs a script from the internet without reading it. Only do this for sources you fully trust.

sudo <anything copied>Danger

Gives full admin power to a command you may not understand.

chmod -R 777Danger

Lets anyone read, write, and run everything. It is a security hole, not a fix.

> important.txtDanger

A single > overwrites a file instantly. Use >> to append.

The big picture

Git

A version control system installed on your computer. It tracks every change as a snapshot called a commit.

GitHub

A cloud service that stores Git repos online. It adds Pull Requests, reviews, issues, and project pages.

Why it matters

You can undo almost any mistake and work in parallel with teammates. Every tech company uses it.

02 — Important points

Golden rules

Read git status constantly

It tells you where you are and usually prints the exact next command.

Commit small and often

One logical change per commit makes history readable and undo painless.

Pull before you start, push when you finish

Syncing often keeps conflicts small and rare.

One branch per task

Never develop directly on main in a team. Branches are cheap, so use them.

Never rewrite shared history

Don't reset, amend, or rebase commits others already pulled. Use git revert instead.

--force-with-lease, never --force

It refuses to overwrite work you haven't seen yet.

Never commit secrets

Put .env in .gitignore before your first commit. Pushed secrets must be treated as leaked.

Almost nothing is truly lost

Committed work can be recovered with git reflog. Uncommitted work cannot, so commit often.

06 — Most used

Core commands

These sixteen cover about 90% of daily Git work.

git init

Turns the current folder into a Git repository. Run it once per project.

git clone <url>

Downloads a repo with its full history. It also sets up origin for you.

git status

Shows what changed, what is staged, and what to do next.

git add <file> | .

Moves changes into the staging area. . means everything in this folder.

git commit -m "msg"

Saves a snapshot of staged changes with a message.

git log --oneline

Lists commit history. Add --graph --all to see branches.

git diff

Shows unstaged line changes. --staged shows what will be committed.

git branch

Lists branches. -d name deletes a merged one.

git switch -c <name>

Creates a new branch and moves to it. Drop -c to switch to an existing one.

git merge <branch>

Brings another branch's commits into the current branch.

git remote -v

Shows connected remotes and their URLs.

git push

Uploads local commits. First push of a branch needs -u origin <branch>.

git pull

Fetches remote commits and merges them into your branch.

git fetch

Downloads remote changes without touching your files. A safe way to peek.

git restore <file>

Discards uncommitted edits. --staged unstages instead.

git stash

Shelves uncommitted work temporarily. git stash pop brings it back.

The three tools: restore vs reset vs revert

git restoreFiles

Changes files in your working directory or staging area. It never touches commit history.

git resetRewrites

Moves your branch pointer back to an older commit. Only use it on commits you haven't pushed.

git revertSafe for teams

Adds a new commit that does the opposite of an old one. History stays intact.

09 — Full flow · working together

Team flow

The GitHub flow: everyone works on their own branch, and changes reach main only through reviewed Pull Requests.

The 10-step team loop

Get the project

Clone once. Every later session starts at step 2.

git clone git@github.com:team/project.git
cd project

Start from the latest main

Never begin a task on an outdated base.

git switch main
git pull

Create a task branch

Name it by type and topic: feature/, fix/, docs/, chore/.

git switch -c feature/login-form

Work in small commits

Commit each logical step with a clear message.

git add src/login.html
git commit -m "feat: add login form markup"

Push the branch

-u links it to the remote so future pushes are just git push.

git push -u origin feature/login-form

Open a Pull Request

On GitHub click Compare & pull request. Describe what changed, why, and how to test it.

# or from the terminal with GitHub CLI
gh pr create --fill

Review & feedback

Teammates comment; you fix and push again. The PR updates automatically.

git commit -am "fix: address review comments"
git push

Stay in sync with main

If main moved while you worked, bring it into your branch and resolve conflicts locally.

git fetch origin
git merge origin/main
git push

Merge the PR

After approval and green checks, click merge on GitHub (merge, squash, or rebase).

Clean up

Delete the branch and go back to an up-to-date main for the next task.

git switch main
git pull
git branch -d feature/login-form
git fetch --prune

10 — Scenarios · when changes collide

Merge conflicts

A conflict happens when two branches change the same lines, or one edits a file the other deleted. Git pauses and asks a human to decide; it is normal, not an error.

What a conflict looks like inside the file

Git writes both versions between markers. Everything between the markers must become one final version.

index.html — conflict
Accept Current Change|Accept Incoming Change|Accept Both Changes|Compare Changes
<nav>...</nav>
<<<<<<< HEAD
<h1>Welcome</h1>
=======
<h1>Hello RevoU</h1>
>>>>>>> feature/greeting
<p>Intro text</p>

Read the markers

<<<<<<< HEADStart of your current branch's version.
=======Divider between the two versions.
>>>>>>> branchEnd of the incoming branch's version.
!
Ours vs theirs flips during rebase. In a merge, "current/ours" = your branch. In a rebase, "current/ours" = the branch you rebase onto (e.g. main), and "incoming/theirs" = your commits.

Universal resolution flow

Don't panic, read status

Conflicted files are listed under "Unmerged paths" as both modified.

git status
git diff --name-only --diff-filter=U

Open each file and decide

Keep current, incoming, both, or write a new combined version. Delete all three marker lines.

Search for leftover markers

A forgotten <<<<<<< will break your code.

grep -rn "<<<<<<<\|>>>>>>>" .

Test that it still works

Open the page or run the tests before you continue.

Mark as resolved

git add tells Git this file is now fixed.

git add index.html

Finish the operation

Use the command that matches what you were doing.

# merge or pull
git commit
# rebase
git rebase --continue
# cherry-pick / revert
git cherry-pick --continue
git revert --continue
⏏
Panic button: git merge --abort, git rebase --abort, or git cherry-pick --abort returns everything to how it was before you started.

How to prevent conflicts

Pull often

Merge main into your branch daily, not once at the end.

Small, short-lived branches

A branch that lives two days conflicts far less than one that lives two weeks.

Talk about shared files

Tell teammates before editing hot files like the navbar or global CSS.

Same formatter for everyone

Use Prettier with one config so formatting never creates fake conflicts.

12 — Rare but must know

Rare commands that save the day

git reflogLifesaver

A diary of everywhere HEAD has been, including "deleted" commits. Your ultimate undo button.

git revert <hash>Rare

Creates a new commit that reverses an old one. The safe undo for shared branches.

git resetCareful

Moves the branch back in time with --soft, --mixed, or --hard. Never on pushed commits.

git cherry-pick <hash>Rare

Copies one specific commit from another branch onto yours.

git rebase -i HEAD~3Careful

Edit the last N commits: reorder, squash, rename, or drop. Only on unpushed work.

git bisectRare

Binary-searches history to find exactly which commit introduced a bug.

Shows who last changed each line and in which commit.

git add -pRare

Stage changes chunk by chunk, so one messy file becomes clean focused commits.
